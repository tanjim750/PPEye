# PPEye Business Flow (Phase A code-grounded update)

Evidence below refers to repository-relative paths and the line numbers in the checked-in files at the time this document was written. “Live” means the code queries or mutates Supabase; “demo/local” means hardcoded or in-memory UI state. This documents code paths, not a claim that deployed credentials or remote services are configured.

## 1. Roles and access

- **Vendor (external)** is represented in `users.category = EXTERNAL`, with `external_type` `PROJECT_MANAGER`, `TEAM_LEADER`, or `WORKER` (`docs/sql/legacy-ppeye-postgres-schema.sql:8-13,32-44`; `src/types/database.types.ts:9-14`). App permission logic grants PM and Team Leader submission/draft/feedback/resubmission; only PM can manage team; Worker is denied those capabilities by this helper (`src/services/vendor/vendorRole.service.ts:24-82`). Unknown external type defaults permissively for submissions (`src/services/vendor/vendorRole.service.ts:69-81`), which is a fallback, not an explicit role.
- **Reviewer/internal** is `category = INTERNAL`; login calls Supabase Auth, resolves the PPEye user by Auth email, and maps the real app user id/category/external type (`src/features/auth/services/auth.service.ts:8-79`; `src/services/supabase/auth.ts:4-10`). External accounts must resolve exactly one `vendor_members` row; its profile ID is stored in auth state (`auth.service.ts:33-57`; `LoginScreen.tsx:70-88,98-155`). Routing remains external for vendors and internal for reviewers. Demo users load only inside the dev-flag branch (`LoginScreen.tsx:116-134`; `src/constants/devMode.ts:1-5`).
- **Admin** is not a distinct database role. Generic Add User now explains that it does not create an account (`src/features/users/AddUserScreen.tsx:58-76`). Vendor team service can create/link a public profile but cannot create Supabase Auth credentials (`src/services/vendor/vendorTeam.service.ts:93-159`); its success copy says a matching Auth account must also be created (`src/features/team/VendorTeamScreen.tsx:99-110`).
- `vendor_profiles` holds vendor and project identity; `vendor_members` links a user to a profile. Submission rows hold `vendor_profile_id` and `submitted_by` (`docs/sql/legacy-ppeye-postgres-schema.sql:57-84,66-71`). The app uses membership as the intended organization boundary. The user-provided deployed policy rows (2026-10-20) show broad `anon` read/write and authenticated unrestricted policies across `users`, vendor tables, submissions, images, reviews, and reasons. Those policies permit the login and vendor lookup queries under the authenticated role, but do not enforce vendor isolation.
- Vendor UI uses the profile ID resolved at login; a missing profile now produces an error instead of selecting profile 1 (`src/services/vendor/useVendorDashboard.ts:28-43`; `src/features/team/VendorTeamScreen.tsx:58-73`; `src/features/submissions/components/SubmissionReviewScreen.tsx:610-616`). Policy evidence confirms SELECT is permitted on `users`, `vendor_members`, and `vendor_profiles` for authenticated sessions; this is policy-level confirmation, not a live credential/API smoke test.

## 2. Data model in plain words

Schema source: canonical `supabase/migrations/20261015000000_init_ppeye_schema.sql` (and historical reference in `docs/sql/legacy-ppeye-postgres-schema.sql`); generated row shapes are in `src/types/database.types.ts`.

- `users`: identity/contact, `category`, external subtype, active flag, and optional profile image file link (`docs/sql/legacy-ppeye-postgres-schema.sql:32-44`).
- `vendor_profiles`: vendor/project names and creator (`docs/sql/legacy-ppeye-postgres-schema.sql:57-64`). `vendor_members`: many-to-many organization membership (`docs/sql/legacy-ppeye-postgres-schema.sql:66-71`; unique pair `docs/sql/legacy-ppeye-postgres-schema.sql:232-235`).
- `ppe_submissions`: one site check, vendor, submitting user, JSON metadata, status and timestamps (`docs/sql/legacy-ppeye-postgres-schema.sql:73-84`). Metadata is used by UI for GPS/weather/count/review summary (`src/features/submissions/components/SubmissionReviewScreen.tsx:608-631`; `src/features/reviews/services/reviews.service.ts:507-591`).
- `ppe_worker_instances`: worker sequence within one submission (`docs/sql/legacy-ppeye-postgres-schema.sql:86-91`; unique submission+sequence `docs/sql/legacy-ppeye-postgres-schema.sql:237-239`). No worker name field exists in schema.
- `files`: provider (default Drive), provider ID, filename, MIME, size, creator (`docs/sql/legacy-ppeye-postgres-schema.sql:46-55`). A later migration adds `drive_id` (`supabase/migrations/20261017000002_add_drive_id_to_files.sql:1-16`); service has compatibility fallback if `provider_file_id` is missing (`src/services/supabase/ppeyeDb.service.ts:120-160`).
- `ppe_images`: one file relation per worker and side FRONT/BACK (`docs/sql/legacy-ppeye-postgres-schema.sql:93-99`; unique worker+side `docs/sql/legacy-ppeye-postgres-schema.sql:243-245`). `other_images`: optional submission-level site/context photo (`docs/sql/legacy-ppeye-postgres-schema.sql:101-107`).
- `ppe_reviews`: worker verdict + reviewer + timestamp (`docs/sql/legacy-ppeye-postgres-schema.sql:109-115`). `unsafe_reasons` is the catalog (`docs/sql/legacy-ppeye-postgres-schema.sql:117-123`; seeded helmet, harness, lanyard, anchorage, shoes, other `:303-314`). `ppe_review_reasons` links a review to reason with optional note (`docs/sql/legacy-ppeye-postgres-schema.sql:125-131`).
- `other_reviews`: submission-level verdict/reason for non-PPE evidence (`docs/sql/legacy-ppeye-postgres-schema.sql:133-140`). `submission_reviews`: overall submission verdict/reason (`docs/sql/legacy-ppeye-postgres-schema.sql:142-149`). Reviewer completion now writes per-worker `ppe_reviews`, `ppe_review_reasons`, and one `submission_reviews` row before marking the parent `COMPLETED` (`src/features/reviews/services/reviews.service.ts:947-1007`).
- `system_settings`: **not present** in either supplied schema nor generated database types (`src/types/database.types.ts:16-18,379-392`; `docs/sql/legacy-ppeye-postgres-schema.sql:31-315`).
- FK relationships are declared by script (`docs/sql/legacy-ppeye-postgres-schema.sql:151-230`); generated TypeScript says `Relationships: []` (`src/types/database.types.ts:59,95,122,143,182,203,227,251,275,299,323,350,378`), so generated types do not reflect those joins.

## 3. Status model

Database enums: submission `DRAFT`, `SUBMITTED`, `UNDER_REVIEW`, `COMPLETED`; worker verdict `SAFE`/`UNSAFE`; image side `FRONT`/`BACK` (`docs/sql/legacy-ppeye-postgres-schema.sql:15-25`; `src/types/database.types.ts:9-14`). There is no worker status column: worker UI state derives from its review row or defaults to review/pending (`src/services/vendor/vendorSubmissions.service.ts:216-247,249-270`; `src/services/submissions/services/workerChecks.service.ts:661-683`).

Transitions evidenced in code:

```text
Vendor DRAFT --submit after FRONT+BACK for >=1 worker--> SUBMITTED
SUBMITTED --reviewer saves draft / exits early--> UNDER_REVIEW
SUBMITTED or UNDER_REVIEW --reviewer completes--> COMPLETED
COMPLETED (unsafe worker corrected) --vendor replaces evidence--> SUBMITTED
```

Evidence: draft create `src/services/vendor/vendorSubmissions.service.ts:631-660`; submission validation and set `SUBMITTED` `:733-804`; reviewer draft status/metadata update `src/features/reviews/services/reviews.service.ts:865-933`; completion writes relational verdicts before setting `COMPLETED` `:935-1015`; unsafe resubmit sets `SUBMITTED` `src/services/vendor/vendorSubmissions.service.ts:846-885`.

UI mapping: `DRAFT` -> saved draft; `SUBMITTED` -> pending; `UNDER_REVIEW` -> waiting/in-progress draft; `COMPLETED` -> safe or unsafe from current worker reviews. Per worker, latest review is current only if its timestamp is at least the active photo timestamp; a newer replacement makes the row pending/review (`src/services/vendor/vendorSubmissions.service.ts:14-29,389-435,515-600`; `src/features/reviews/services/reviews.service.ts:522-563`).

Worker verdict sequence is selected in the reviewer component; every worker needs SAFE or UNSAFE before completion, and UNSAFE needs at least one reason with text for Other (`src/features/reviews/ReviewDetailScreen.tsx:660-790,807-859`; service validation and writes `src/features/reviews/services/reviews.service.ts:935-1007`).

## 4. Vendor workflow, step by step

1. **Home**: external home uses the resolved vendor profile and real Supabase metrics/checks; missing profile becomes a visible hook error (`src/services/vendor/useVendorDashboard.ts:10-47`; `src/services/vendor/vendorSubmissions.service.ts:142-181`). Role gating is via permission helper (above). `app/(external)/index.tsx:1-3` maps the route. Live RLS access is not yet verified.
2. **Capture workers**: `(external)/capture` and `continuous-ppe-capture` both map to `CaptureScreen` (`app/(external)/capture.tsx:1-3`; `app/(external)/continuous-ppe-capture.tsx:1-3`). Each worker receives FRONT then BACK; complete pairs advance to next worker, captures are retained as pending local state (`src/features/capture/hooks/useContinuousPPECapture.ts:140-236`). Camera permission/readiness/error states are in `src/features/capture/CaptureScreen.tsx:44-74`; Done is enabled only with at least one complete worker and no incomplete pair (`:82-119`).
3. **Optional other/site photos**: `capture-others` maps to `OthersCaptureScreen`; photos are locally held and may have prompts for access ID, rooftop, banners, first-aid box (`app/(external)/capture-others.tsx:1-3`; `src/features/capture/OthersCaptureScreen.tsx:40-78`). They are optional relative to core worker pairs in the submission validator call (`src/features/submissions/components/SubmissionReviewScreen.tsx:494-502`).
4. **Review before submit**: `submission-review` builds capture timestamp + GPS + weather; weather may use live/cache/estimated fallback (`src/features/submissions/components/SubmissionReviewScreen.tsx:185-267`; `src/services/weather/weather.service.ts:12-37,59-91,160-233`). Exact image-pair validation runs before submit (`SubmissionReviewScreen.tsx:494-514`). Sample workers appear only when the dev flag is on (`SubmissionReviewScreen.tsx:163-175`; `src/constants/devMode.ts:1-5`).
5. **Submit**: submission review passes the resolved vendor profile ID and app user ID (`SubmissionReviewScreen.tsx:608-643`). Missing IDs stop creation; `createPPESubmissionHeader` no longer selects the first database user/profile as fallback (`src/services/supabase/ppeyeDb.service.ts:174-225`). The DB helper creates submission and worker rows, then registers files and image relations (`ppeyeDb.service.ts:174-383`). The app broadcasts the header before background Drive upload finishes (`SubmissionReviewScreen.tsx:546-647`).
6. **Waiting / history**: history route maps to `SubmissionHistoryScreen` (`app/(external)/history.tsx:1-3`), which queries vendor submission service; statuses are grouped as safe/unsafe/review and worker rows can open details (`src/services/vendor/vendorSubmissions.service.ts:338-449`; `src/features/submissions/components/SubmissionHistoryScreen.tsx:43-120`). Detail fetch gets worker photos, reasons and submission review (`src/services/vendor/vendorSubmissions.service.ts:457-589`).
7. **Unsafe correction loop**: action-required details use live worker verdict/reason/photo when available; sample unsafe details/photos only appear in demo mode (`SubmissionDetailsActionRequiredScreen.tsx:77-205,315-440`). Missing live item shows unavailable. Corrected evidence replaces the active image row, timestamps the replacement, and moves the parent to `SUBMITTED` (`src/services/vendor/vendorSubmissions.service.ts:846-885`; storage update `src/services/storage/ppe-images.ts:755-768`). The old review stays as history but no longer applies to the newer image.

## 5. Reviewer workflow, step by step

1. Queue route `/reviews` -> `ReviewQueueScreen`; internal home `/` -> `InternalHomeScreen`; history -> `ReviewHistoryScreen` (`app/(internal)/reviews.tsx:1-3`, `index.tsx:1-3`, `history.tsx:1-3`). `useReviews` does initial/foreground refresh and one ref-counted Realtime channel while mounted (`src/features/reviews/services/reviews.service.ts:303-318,638-728,1115-1140`). Live query reads up to 50 submissions and worker/review/image relations (`:477-515`).
2. Open queue item -> `ReviewDetailScreen`, loads worker instances/photos (`ReviewDetailScreen.tsx:470-555`). Live image failures show unavailable/error UI; sample photos render only in dev demo mode (`ReviewDetailScreen.tsx:1021-1043,1154-1177`).
3. Reviewer can have up to **3 in-progress drafts owned by that reviewer**; local/UI guard plus persisted `reviewDraft.reviewerId` records draft ownership (`ReviewQueueScreen.tsx:123-157`; `src/features/reviews/services/reviews.service.ts:367-386,865-933`). Draft verdicts are serialized to submission metadata for cross-device recovery, subject to deployed RLS.
4. Per worker, select SAFE or UNSAFE, with required unsafe reasons and note for Other (`ReviewDetailScreen.tsx:660-790,807-859`). Completion writes relational per-worker verdicts/reasons, overall submission review, metadata mirror, then parent `COMPLETED`; failure is shown and does not claim success (`src/features/reviews/services/reviews.service.ts:935-1015`; screen `ReviewDetailScreen.tsx:808-835`).
5. Vendor reads latest current relational review first and metadata mirror when current; replacement photo timestamp invalidates older verdict (`src/services/vendor/vendorSubmissions.service.ts:14-29,515-600`). Deployed RLS and Realtime membership must still be verified separately.

## 6. Business rules and constraints

- Every worker needs one FRONT and one BACK and at least one worker; draft submit service enforces both (`src/services/vendor/vendorSubmissions.service.ts:771-788`). Capture UI also blocks Done for incomplete pairs (`src/features/capture/CaptureScreen.tsx:82-119`). Image validator called on review screen (`src/features/submissions/components/SubmissionReviewScreen.tsx:494-514`).
- Other/site images are optional in standard submission validation (`src/features/submissions/components/SubmissionReviewScreen.tsx:494-502`); an “other” capture prompt includes four named examples but source does not establish all four as a DB-level required set (`src/features/capture/OthersCaptureScreen.tsx:40-56`).
- PM can manage vendor team; Team Leader and Worker cannot per role helper (`src/services/vendor/vendorRole.service.ts:28-67`). Team service allows creating only Team Leader/Worker, requires name/phone, checks internal-user conflict, links `vendor_members`, and unique membership is DB-enforced (`src/services/vendor/vendorTeam.service.ts:86-177`; `docs/sql/legacy-ppeye-postgres-schema.sql:233-235`).
- Password rules: Supabase Auth owns passwords; there is no app password column or password-hash migration. Login uses email/password; change password calls Auth `updateUser`, and Forgot Password calls `resetPasswordForEmail`, surfacing returned errors (`src/services/supabase/auth.ts:4-18`; `src/features/settings/ChangePasswordScreen.tsx:30-68`; `src/features/auth/components/ForgotPasswordScreen.tsx:30-56`). Change password UI requires at least 6 characters and matching values (`ChangePasswordScreen.tsx:31-48`).
- Language choice is persisted by onboarding preference and i18n supports English/Bangla (`src/services/onboarding/languagePreference.ts`; `src/i18n/config.ts`; route `app/(onboarding)/language.tsx`). Exact fallback behavior: default language/fallback language in `src/i18n/config.ts` and `src/i18n/index.ts:41`.
- Notifications screen/settings and Expo push service exist (`src/features/notifications/NotificationSettingsScreen.tsx:1-4`; `src/services/notifications/expoPush.ts`), but no server-side notification trigger/worker was found in scanned schema/functions. Avoid assuming verdict notifications are delivered.
- DB uniqueness: vendor member pair, worker sequence per submission, file provider ID per provider, one side per worker, file uniqueness per image link, one reason per PPE review (`docs/sql/legacy-ppeye-postgres-schema.sql:232-264`). No explicit allowed status-transition trigger/check is defined; transitions are app code.
- No code-enforced worker count maximum found in the inspected capture/submission paths. Reviewer draft maximum is three in UI/local logic, not a DB constraint (`src/features/reviews/components/InProgressLimitModal.tsx:83-89`).

## 8. What is real vs what is demo

**Supabase-backed code paths (remote API behavior not smoke-tested here):** Supabase Auth sign-in/reset/update; PPEye user and membership lookup; vendor dashboard/history/detail/team reads; submission creation and file links; reviewer relational writes and sync (`src/features/auth/services/auth.service.ts:8-79`; `src/services/supabase/auth.ts:4-21`; `src/services/vendor/vendorSubmissions.service.ts:142-181,356-600`; `src/services/supabase/ppeyeDb.service.ts:174-383`; `src/features/reviews/services/reviews.service.ts:477-615,935-1015`). User-provided policy rows confirm the necessary authenticated query permissions, while reported Realtime availability is false for six tables; see Open questions.

**Demo/local paths and fallbacks:**

- Dev demo login reads `dummyUsers`; release login only uses Supabase Auth (`src/features/auth/components/LoginScreen.tsx:116-155`; `src/constants/devMode.ts:1-5`).
- Reviewer and vendor fixtures are seeded only in demo mode, carry `isDemo`, and show a DEMO label (`src/features/reviews/services/reviews.service.ts:81-294`; `src/features/submissions/services/workerChecks.service.ts:38-213`; queue/history/home row components).
- Sample capture/reviewer/action-required photos and fallback identities are flag-gated; release with no real image uses placeholder/unavailable UI (`src/features/submissions/components/SubmissionReviewScreen.tsx:163-175`; `src/features/reviews/ReviewDetailScreen.tsx:1021-1043,1154-1177`; `src/features/submissions/components/SubmissionDetailsActionRequiredScreen.tsx:77-205`).
- Real account/user/vendor IDs are resolved from Auth email and `vendor_members`; missing IDs no longer fall back to 1 or the first database row (`src/features/auth/services/auth.service.ts:16-57`; `src/services/supabase/ppeyeDb.service.ts:174-225`).
- Error fallbacks may render apparently successful zero metrics / empty screens (`src/services/vendor/vendorSubmissions.service.ts:164-181,314-332,374-380`; `src/services/vendor/vendorTeam.service.ts:62-65`).
- Weather fallback estimates values and can reuse cached weather; these should not be represented as measured current weather (`weather.service.ts:59-91,160-233`).
- `src/features/users/AddUserScreen.tsx:58-76` is not connected to account creation and explicitly reports that fact.
- Tests contain mocks, but those are test fixtures and not app business data (`src/**/__tests__/**`).

## 9. Open questions and risks

1. **Deployed RLS permits current queries but does not isolate vendors:** user-provided 2026-10-20 results list `Allow all ... USING true WITH CHECK true` policies for authenticated users and `anon` SELECT plus ALL policies for `files`, all PPE submission/review tables, `other_images`, `other_reviews`, `users`, `vendor_members`, and `vendor_profiles`. This permits the app's authenticated user/profile/membership reads and its data reads/writes, but it also permits unrestricted cross-vendor access and anonymous writes. The repo's restrictive migration is `supabase/migrations/20261017000000_vendor_role_and_isolation_rls.sql`; no SQL was applied in this work. Realtime status was provided only for `files`, `ppe_review_reasons`, `ppe_reviews`, `ppe_submissions`, `submission_reviews`, and `unsafe_reasons`, all marked false.
2. **Auth email is the identity bridge:** schema has no `auth_user_id` column (`supabase/migrations/20261015000000_init_ppeye_schema.sql:34-45`), so login matches Auth email to one active `public.users` row, then resolves membership (`src/features/auth/services/auth.service.ts:16-57`). Confirm Auth emails exactly match the intended PPEye users. No password storage column is used.
3. **Reviewer write is not transactional:** completion writes multiple worker/reason/overall rows before marking `COMPLETED`; an intermediate failure is shown and leaves the parent uncompleted, but earlier rows may remain and retry may append additional history rows (`src/features/reviews/services/reviews.service.ts:947-1015`; schema indexes are not unique for review histories `supabase/migrations/20261015000000_init_ppeye_schema.sql:327-338`).
4. **Submission status ambiguity:** reviewer queue considers `UNDER_REVIEW` a draft/in-progress (`src/features/reviews/services/reviews.service.ts:551-553`), yet this status also represents submissions currently under review. What distinction is intended between waiting and reviewer-owned draft?
5. **Re-review after unsafe resubmission:** old review rows are retained; current logic invalidates them by comparing review time to active image time (`src/services/vendor/vendorSubmissions.service.ts:14-29,515-600`; replacement timestamp `src/services/storage/ppe-images.ts:755-768`). Verify this under deployed policies.
6. **Schema sources differ:** `docs/sql/legacy-ppeye-postgres-schema.sql` and initial migration create broad anon/authenticated policies (`docs/sql/legacy-ppeye-postgres-schema.sql:281-301`; `supabase/migrations/20261015000000_init_ppeye_schema.sql:340-373`). Later migration drops them on core submission/review/member/profile tables and defines scoped replacements (`supabase/migrations/20261017000000_vendor_role_and_isolation_rls.sql:51-66,68-127,129-140`). User-provided deployed results still show the broad policies on six tables, so deployed migration state differs from that intended sequence.
